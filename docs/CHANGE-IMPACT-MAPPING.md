# Change-impact mapping — same-change regression contract

Roadmap: **P2 — implement fast, deterministic feedback for small PR changes; update tests in the same change as behavior.** This is a navigation/review contract, not a second specification, test registry or CI selector. [System Spec](VAcleaner-SYSTEM-SPEC.md) owns behavior; [registry](../config/qa-suites.json) owns suite membership; [package scripts](../package.json) own command implementations. Read their current versions rather than copying this document into another checklist.

## Authority and scope

Use [Engineering Standard](ENGINEERING-STANDARD.md), the unchanged [Roadmap](DEVELOPMENT-ROADMAP.md), and System Spec REL-001/002/003/005, AI-RULE-004/007/011/012. **Current REL-001/003 and AI-RULE-004 take precedence over the historical v4.2.34 change-record statement that a separate QA branch was optional.** Each approved task uses its own branch/PR and a local release candidate; main remains production-only. No historical record authorizes direct experimentation on main.

This mapping adds no runtime behavior, dependencies, test selection, workflow topology or release exception. IP-01 does not implement deduplication/parallelism (IP-03/IP-04), claim a 20% CI reduction or reopen G09. Examples below are hypothetical future changes requiring their own approved scope, not changes performed by this document.

## Required evidence unit

For each materially affected behavior, put one row in the existing PR description, linking this mapping instead of copying a suite list:

`user-visible before → intended after | authoritative source → artifact | Spec contract/change | targeted command + exact case/assertion | positive result | negative/control result | full-gate evidence/blocker`.

The description must explain **why the test would detect the wrong behavior**, not just say a test file changed. For a behavior fix, where practical demonstrate the relevant regression failing against old behavior and passing against the change in an isolated fixture, without disabling unrelated guards. Otherwise explain why a direct old-version run is unsafe/inapplicable and supply a meaningful wrong-input/state control. For intentional behavior changes, distinguish the new expected outcome from accidentally preserving the old assertion. Include specification and regression changes in the same PR; no later “tests catch up” PR.

For a mixed change, cover all affected rows. A targeted green result is early feedback, not permission to skip canonical QA. Evidence records source/head SHA, command, runtime/artifact root, expected and actual result, and safe log/screenshot reference. Redact PII/tokens; never paste a private audit/review package into a public PR.

## Artifact and full-gate references

- **C — canonical:** `npm run build` creates `dist`; `npm run verify:artifact` checks it. Build/stamping commands may regenerate outputs: use an isolated release-candidate checkout and inspect the diff. Do not hand-edit generated copies.
- **N — normal operations:** [candidate builder](../scripts/build-admin-release-candidate.mjs) consumes C plus `sandbox/ui.js`, `sandbox/ui.css`, `sandbox/forms.js`, `sandbox/forms.css`, `staging/ui/mobile.css`; `npm run build:release-candidate` produces `release-candidate-test-results/dist`. Those sandbox/staging files are production inputs. C and N are distinct acceptance targets, not duplicate tests.
- **S — stable migration/rollback:** the stable artifact used by the existing operations workflow is a separate compatibility target. Do not replace it with C/N to remove apparently repeated checks.
- **B — backend fixture/source:** local handler/helper tests with synthetic database/transport; these do not certify deployed state, RLS or multi-connection races. Deployed validation requires separately approved isolated scope.
- **F — mandatory full acceptance:** [REL-002/003 and the System Spec](VAcleaner-SYSTEM-SPEC.md), [release checklist](CI-SELECTIVE-VALIDATION.md#p2--release-acceptance-checklist-reviewed-against-main-githubworkflowspagesyml), and actual [pages workflow](../.github/workflows/pages.yml) remain authoritative. Preserve static/build/artifact contracts, canonical Browser aggregate, WebKit/mobile and all four operations engine×viewport variants on the validated artifacts, plus the separate scope workflow. Main deployment must wait for all required successes and reuse the accepted artifact without rebuilding. Deployment/provenance/live readback and physical device evidence are separate. Targeted commands below do not replace any part of F.

The existing classifier alone determines whether a PR qualifies for its existing docs-only lane. Do not manually label a code/mixed/workflow change docs-only; every main release retains the full contract. Check current runtime pins in the workflow. A mismatched local browser environment is supplementary/BLOCKED for pinned acceptance, never equivalent GREEN; do not install dependencies merely to make this mapping executable.

## Representative PR evidence examples

These examples specify what a reviewer should look for; they are not executed results or approval of product work.

1. **Compiled admin UI:** proposed keyboard/Back layout adjustment names `sandbox/forms.*` or `sandbox/ui.*` as source, N as observed artifact and the canonical handler it delegates to. Run builder/static contracts before navigation/browser checks. Evidence: visible action and return context; negative mobile overlay/keyboard condition; screenshot of actual N at affected widths. A screenshot from raw C cannot certify N.
2. **Public:** proposed draft bootstrap change cites PUBBOOK-003 and the owning script. Pair restored-draft positive with empty/cleared/no-write negative, using `test:public-draft-bootstrap`, then hydration/browser fixtures. A new label snapshot alone cannot prove draft preservation.
3. **Backend:** proposed handler validation change cites the status/availability contract, source helper and synthetic DB fixture. `test:backend-logistics` demonstrates authorized persisted outcome vs invalid/forbidden/conflict with no write. Explicitly mark real Postgres races and VA HOME-only identity validation unverified unless separately approved isolated tests exist. No production query is an early validation command.
4. **Finance/settings:** proposed error presentation change pairs valid acknowledged response with rejected/invalid/malformed responses from `test:admin-settings-errors`; explain why local writes remain zero on failure. Run finance/deposit checks for calculation effects. If user interaction/persistence changes, add affected browser acknowledgement + reload evidence in that future PR; do not claim these helper tests close G09 or diagnose its cause.
5. **PWA:** proposed worker/session change pairs controlled-ready/reconnect with uncontrolled/activation-delayed or terminal/outage cases. Preserve C/N/S migration scenarios, version coherence and native evidence boundaries. Mark unavailable physical iPhone acceptance BLOCKED, not filled by Linux WebKit.
6. **Workflow:** proposed future classifier/tooling change pairs allowed ordinary docs with mixed/code/config/rename/missing-list denials, then validates failed-gate deployment rejection and artifact reuse. Deterministic fixtures precede hosted CI; actual startup/matrix/production acceptance remains separate. This example does not authorize IP-03/IP-04 or changes to pages.yml.

## Targeted local validation order before costly CI

1. Confirm current main, approved scope and actual diff including renamed/generated/compiled inputs. State the Roadmap bullet and decide behavior-changing vs no-behavior-change with evidence. Read relevant Spec and trace source→artifact→caller. If unknown, resolve or report BLOCKED before claiming coverage.
2. Choose the affected table rows; inspect the current command implementation and fixtures for safe local/synthetic transports. Identify expected positive and meaningful negative outcomes **before** modifying behavior/assertions. Do not run live backend/notification commands as local smoke.
3. Run cheap affected source/helper/contract checks first. Fix the first in-scope failure and update its Spec/regression in the same change. Preserve first-failure evidence; do not increase timeouts, force-click, weaken assertions or rerun a whole journey to hide a failure.
4. Build/verify the current isolated C and, where affected, N. Run relevant browser scenarios against the explicitly named artifact using the existing pinned environment when available. Record unmet environment/device prerequisites; no arbitrary dependency install or Docker download loop.
5. Perform semantic diff, negative-case and screenshot review. Record exact SHA, results, skipped/blocked scope and no-behavior reasoning in the existing PR template. Do not submit “targeted green” as full acceptance or start expensive CI to discover an already known local contract failure.
6. Execute the applicable complete local QA required by REL-002/AI-RULE-007 (canonical static/browser via existing commands and all locally available workflow checks), then the unchanged PR/main release gates. Use the existing workflow policy, not this table, to determine automatic checks. First failure: retain evidence and diagnose before any permitted rerun. CI green, deployment, live acceptance and physical device checks stay separate.

## Justified no-behavior-change path

No artificial regression edits are required solely to touch a test file. A documentation-only change states why it cannot affect runtime, test membership, build inputs or selection. A code refactor states the preserved observable contract and demonstrates equivalence with the relevant unchanged tests, inputs/outputs, source→artifact audit and negative cases. Config/build/generated/compiled/interaction changes cannot be declared harmless merely by filename or unchanged screenshots.

If an existing regression already covers the intended outcome, cite its exact case/assertion and demonstrate it is discriminating; explain why no test modification is needed. A behavior change still updates its canonical specification and adequate regression evidence in the same PR. Missing/disputed coverage requires an in-scope test update or BLOCKED status, not an empty “no tests needed” field. Relevant code-path Spec-touch guards and full gates remain mandatory even for refactors; this path grants no bypass. Cosmetic docs edits need no invented product release/version bump unless applicable policy requires it.

## What is enforced, and what remains human review

| Mechanism | Actual automatic boundary | Reviewer responsibility |
| --- | --- | --- |
| [Spec guard](../scripts/check-system-spec.mjs) | Required tokens/release metadata and selected changed-path→Spec-touch check in supported CI events | Correct contract and semantic description; compiled sandbox/staging impact is not comprehensively inferred by its current patterns |
| [Roadmap scope guard](../scripts/check-roadmap-scope.mjs) | Applicable PR metadata/path policy with existing exemptions | Correct phase/bullet, authorized scope and no unrelated work; marker presence is not owner approval |
| [Classifier](../scripts/classify-pr-changes.mjs) / actual workflow | Existing fail-closed docs-only classification and configured full deployment success conditions | Correct source/test impact; a skip never certifies product behavior |
| Registry, scripts, artifact checks | Existing suite execution and assertions; exact artifact contracts where configured | Missing behavior/negative cases, helper-vs-browser-vs-persisted boundaries, screenshot quality and real-device gaps |
| PR template + this mapping | **No new automatic semantic enforcement**; descriptive evidence fields | Read linked cases, challenge expected/observed outcomes, verify no-behavior justification and same-change completeness on exact head |
| Repository settings | Separate from YAML; [IP-02 proposal](IP-02-REPOSITORY-ENFORCEMENT-PROPOSAL.md) only | Confirm effective required reviews/checks/bypass before claiming repository enforcement; no settings changed here |

Reviewer dispositions: `accepted / changes required / blocked`, with challenged contract/case and reason. Keep self-review, external review, local tests, CI, deployment/live and physical-device evidence distinct. An agent role label is not independent review evidence.
